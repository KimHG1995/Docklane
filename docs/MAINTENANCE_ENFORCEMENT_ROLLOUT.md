# Maintenance enforcement rollout

## Current implementation
The registered service/node operation lock checks the persisted maintenance row using the **same MySQL connection already holding resource locks** when `DOCKLANE_MAINTENANCE_ENFORCE=1`. A missing row, DB read failure, invalid generation, or non-OPEN state denies the lock callback. The default is disabled to preserve existing installations until initialization and management authorization exist.

This check is an admission control, **not** an atomic Docker compare-and-update primitive. A mutation already executing past the lock check may still dispatch. Another CP, another manager Agent, external Docker CLI, and a concurrent OPEN→CLOSING transition can race with an in-flight Docker Update.

## Mandatory prerequisites before production enablement
- Scoped ADMIN-only initialization with registered real Swarm identity, audit and irreversible idempotent replay.
- State-transition service checks: CLOSING must close new and queued dispatch; CLOSED requires proof all in-flight requests have settled and manager barriers acknowledged.
- Durable generation/fencing coordination across CP instances; Agent mutation barrier on all managers; restart fail-closed.
- Maintenance release requires reconciliation, cluster binding reassessment and explicit approval.
- MySQL integration tests including 10-connection saturation and stale state transitions; real Docker disposable acceptance.
- Enforcement must be gated at the actual Agent dispatch boundary for long-running operations, not solely at lock acquisition.

Do not enable `DOCKLANE_MAINTENANCE_ENFORCE` in production or declare maintenance complete until those prerequisites pass.

## 2026-10-13 regression corrections (PR #137)
- Startup and periodic **observation-only** service/node/deployment reconciliation now use distinct recovery locks. They retain resource lock and registration checks, but do not use the OPEN admission check. The recovery callbacks must never dispatch a new Docker mutation. Existing client-request paths still require admission.
- Migration v6 converts `owner_id` to utf8mb4 while preserving migration v5's historical checksum. Authentication actor IDs such as `관리자` can be persisted without ASCII conversion failure.
- Maintenance generation is read via `CAST(generation AS CHAR)` before `BigInt`, avoiding mysql2 BIGINT-to-number precision loss. CAS continues to submit decimal strings.
- This does **not** yet block a callback that passed admission before the CLOSING transition, and does not provide an all-manager Agent mutation barrier. The feature stays opt-in and PR remains Draft.
- CI and disposable MySQL acceptance must verify the recovery paths, Unicode migration, large generation and the 10-connection lock scenario before the feature can be promoted.

## Final mutation dispatch read (experimental)
When enforcement is enabled, the registered Agent client now rechecks maintenance `OPEN` immediately before the seven mutating Agent methods. If a resource lock callback is active, the same MySQL connection is used to avoid pool starvation. Inspect, plan and observation-only reconciliation remain permitted. Missing/invalid state and database failure are rejected. The check does not atomically fence an already dispatched HTTP request, a later OPEN→CLOSING transition, or external Docker CLI writers.

**This is not sufficient for closing a cluster:** generation ownership is not yet propagated into an Agent-enforced barrier; already-sent Docker requests remain uncertain. Scoped ADMIN transitions, audit transaction and all-manager acknowledgment still block production rollout. The integration tests for these guarantees must succeed before enabling enforcement.

## Pre-dispatch deterministic denial
A maintenance check executed *before* sending any Agent HTTP mutation now throws `MaintenancePreDispatchRejection`. Only this branded error is added to deterministic rejection classification; generic 409/503 responses or unknown transmission outcomes remain unchanged. Existing durable operation rejection handlers persist FAILED and audit; service/node errors are tagged MAINTENANCE_DISPATCH_REJECTED. Docker request count must be zero. This does not mean the database check and outbound HTTP call are atomic, nor does it make the all-manager barrier complete.

## Operator close request (OPEN → CLOSING only)
Scoped ADMIN may POST `/v1/clusters/:clusterId/maintenance/close-request` with decimal-string `generation` and nonempty `reason`. A single InnoDB transaction updates the expected OPEN generation and inserts the audit event; if the audit insert fails, the transition rolls back. A stale generation fails closed. No API exists yet to enter CLOSED or to reopen: that requires proof of completed in-flight work and acknowledgment from **every manager Agent**, not merely absence of DB operation rows. Existing operations marked NEEDS_ATTENTION and unknown transmitted requests must block automatic rejoin.

This is a partial operator API. It must not be described as a complete maintenance lifecycle or as Docker-native fencing. Production enforcement stays disabled until the remaining acceptance checks pass.

## Unresolved operation readiness snapshot
The maintenance repository can count all service and node operations in PENDING/RUNNING/VERIFYING/NEEDS_ATTENTION using the actual MySQL DB. Missing data, malformed counts, and query failure cause a 503 instead of an optimistic zero. The count is advisory and does **not** grant CLOSED: a zero count does not prove HTTP transmissions or all-manager Agent barriers have drained. In-flight dispatch lease/fencing and manager acknowledgements must be persisted and checked before introducing a CLOSED transition API.

## Readiness API
Scoped ADMIN `GET /v1/clusters/:clusterId/maintenance/readiness` reports durable nonterminal operation count and maintenance generation as decimal strings. `agentBarrierVerified`, `inFlightDispatchVerified`, and `safeToClose` remain **false**, including when the DB count is zero. This is diagnostic only; it is not a manager-barrier implementation, nor authorization to leave/reinitialize the Swarm.

## Durable dispatch and barrier evidence (migration v7)
Two additive tables, `maintenance_dispatches` and `maintenance_agent_barriers`, retain operation send phase and per-manager generation acknowledgements. PREPARED is not proof that a request was never sent after process crash; SENDING/UNCERTAIN must remain unresolved without inspection and operator reconciliation. An ACK row is not sufficient until manager identity and generation are checked against a fixed expected manager membership set. Migration v7 creates no rows, exposes no CLOSED transition, and does not change Agent behavior. Wiring dispatch journaling, lease ownership, generation fencing, multi-Agent acknowledgments, stale process handling and real Docker acceptance remains required. Do not use row counts as a safe-to-close decision.

## Dispatch readiness diagnostic
The readiness API now reports `unresolvedDispatches` as a decimal string from persisted PREPARED/SENDING/UNCERTAIN rows. Query failures deny readiness instead of treating absence of evidence as safe. No runtime writer currently journals these rows and no manager barrier acknowledgements are verified, therefore `safeToClose` remains false even when both counts are zero. Do not enable CLOSED or perform Swarm rejoin based on these diagnostic counts.

## Dispatch journal primitive (not yet wired)
The repository now includes a dispatch journal writer with PREPARED → SENDING → ACKNOWLEDGED/REJECTED/UNCERTAIN transition validation. Database failure when preparing prevents send; SENDING left by a crashed process and UNCERTAIN are never converted into success without independent evidence. This is **only a persistence primitive**: the Agent transport is not yet invoking it, and a second DB checkout while ten resource lock connections are occupied could deadlock the pool. Do not wire it directly or enable enforcement until a scoped connection/dispatch ownership strategy and actual MySQL concurrency acceptance are implemented. A missing journal row is not proof of no in-flight request.

## Journal session reuse
Dispatch journal primitives now optionally accept the active resource-lock MySQL connection, avoiding a second pool checkout under 10/10 lock saturation. This only guarantees session reuse, **not** durable send-fencing when the caller has an uncommitted transaction. Runtime dispatch must still persist PREPARED and SENDING before transport, preserve UNCERTAIN after response loss, retain generation/owner association, and be tested with real concurrent MySQL sessions and Agent failover. Until those invariants are implemented and verified, no CLOSED transition may be exposed.

## MySQL session saturation acceptance
The disposable MySQL 8.4 migration PoC now holds 10 independent resource lock connections and writes PREPARED→SENDING dispatch records through those same sessions. It verifies that all 10 rows remain stored after session release, and forbids UNCERTAIN→ACKNOWLEDGED. This proves only the journal primitive's session reuse and persistence; no actual HTTP request is sent, so transport failure classification, cross-CP fencing and multi-manager acknowledgements are not yet proven.

## Begin-send generation CAS (unwired)
A PREPARED journal entry can advance to SENDING only when the same cluster, operation ID, target manager ID and generation match an OPEN maintenance state in one SQL update. This is a prerequisite for dispatch ownership, not a finished runtime implementation. The statement must commit before HTTP transport. Currently AgentClient mutation signatures do not carry durable operation identity, and manager ACK generation is not enforced. Accordingly beginSend is not yet invoked by the transport, and a race can still occur after the DB check. Keeping the PR Draft avoids mistakenly claiming atomic fencing.

## MySQL beginSend acceptance
The disposable MySQL PoC additionally verifies that a PREPARED record at the active OPEN generation becomes SENDING, while the same old generation is refused after the operator transitions to CLOSING. The rejected row stays PREPARED for conservative reconciliation. The actual Agent HTTP client remains unwired until stable operation identity, manager identity, committed send journal and failover ownership are defined. This test does not demonstrate Docker mutation fencing.

## Journaled transport execution contract (not yet wired to HttpAgentClient)
A typed journal `execute` wrapper accepts the **actual** selected manager Agent ID, durable operation ID, generation, send function and exact definitive-rejection classifier. It writes PREPARED and atomically checks OPEN+generation when moving to SENDING before invoking `send`. Successful Agent responses become ACKNOWLEDGED (acceptance only, not workload convergence); unknown failures become UNCERTAIN; definite pre-update rejection becomes REJECTED. Failure to record a final status leaves an unresolved SENDING record. The wrapper does not itself solve DB transaction commit ordering, multiple CP ownership or the local-Docker SwarmInspect/update race. Since current AgentClient signatures do not propagate operation identity into HttpAgentClient's actual manager selection, runtime integration is intentionally pending rather than inventing an agent ID.

## 2026-10-14 initial runtime transport wiring
The five service/node coordinator mutation call sites now carry the persisted operation ID through AsyncLocalStorage. The registered Agent wrapper scopes the verified maintenance generation and active resource-lock connection; HttpAgentClient chooses the actual manager config.id, journals PREPARED and SENDING, and records success, definite rejection, or uncertainty without replay. A direct raw HttpAgentClient mutation with enforcement ON but without a verified scope is refused. No Agent HTTP/OpenAPI payload field is invented. This is initial runtime wiring only: journal commit ordering under crashes, owner/lease fencing across multiple CPs, expected manager membership and all-manager barrier, and actual Docker failover acceptance still block promotion. A SENDING row after process loss remains unresolved and CLOSED is not permitted.

## Pre-send failure versus response uncertainty
Journal PREPARED/beginSend failures occur before the transport callback is invoked and are raised as `MaintenancePreDispatchRejection` so the existing operation FAILED/audit path can complete without spurious NEEDS_ATTENTION. Even if DB acknowledgement was lost, a partially persisted row remains conservatively unresolved. After the HTTP callback runs, transport loss is never rewritten into deterministic denial; a failed ACKNOWLEDGED journal write surfaces for reconciliation and never replays Docker mutation. Exact Agent pre-update rejections only are marked REJECTED.

## Multi-CP duplicate dispatch lineage (migration v8)
Additive migration v8 places a unique key on (cluster_id, operation_id), refusing pre-existing duplicate evidence rather than deleting history. Retry after a successful DDL but lost migration metadata checks the existing index columns and uniqueness before accepting. Duplicate operation dispatch preparation must not cause another Agent HTTP mutation or be labelled a definite unsent failure: the original operation may have an unresolved SENDING/UNCERTAIN request. Real MySQL PoC asserts eight concurrent duplicate prepare attempts create only one record. This prevents duplicate journal *insertion*, not a distributed executable lease or Docker-native fencing. The registered Agent cannot yet safely declare CLOSED or rejoin solely from this index.

## 2026-10-15 CI and replay review
Migration v8 unit fakes now distinguish the actual information_schema.statistics index-column query from earlier count-only queries. Added regression for a valid already-created unique index and a malformed index, plus a multi-manager replay test: after the first HTTP request has an uncertain outcome, the same durable operation ID cannot create a second journal entry or send again. This is **duplicate-send admission** only; an already-running stale Control Plane can still be beyond its journal check. No all-manager Agent barrier, lease expiry fencing, safe CLOSED transition or disposable Swarm acceptance has been proven. Keep enforcement disabled and PR Draft until end-to-end tests and operational controls exist.

## Agent-local durable barrier prototype (2026-10-15)
Go Agent optionally reads `DOCKLANE_AGENT_MAINTENANCE_STATE_FILE`. When enabled, a missing or invalid file starts fail-closed; GET/PUT `/v1/maintenance/barrier` expose/persist node/cluster/generation and OPEN/BLOCKED. The barrier serializes all seven HTTP mutation handlers against a BLOCKED transition. A successful BLOCKED acknowledgement means handlers accepted before that transition have exited; the persisted state is restored on restart and stale generations are rejected. This is still **not** a complete multi-manager control protocol: manager membership enumeration, authenticated/authorized maintenance actor semantics, all-manager acknowledgement collection, failover and dispatch header propagation from Control Plane, and actual Docker acceptance are outstanding. Do not set this env var in production without the paired Control Plane protocol, and do not authorize CLOSED from this prototype alone. File durability is sync+rename+directory fsync and requires a persistent writable private directory. External Docker CLI writers remain outside the barrier.

## 2026-10-15 all-manager acknowledgement collector (not CLOSED authorization)
The CP collector inspects identity and fresh Swarm manager roster on every configured Agent endpoint without failover, rejects missing/duplicate nodes or mismatch with the expected manager count and Swarm ID, sends a generation-pinned BLOCKED request to every manager, persists ACK rows and rechecks roster/state/generation before returning. Any failed/unreachable manager, stale generation, storage failure or topology mismatch is a **failure**, even if other managers already acknowledged; such partial blocks are not automatically reopened. This collector is not yet exposed as a state-transition endpoint or connected to a transactional CLOSED gate. The Agent PUT is currently protected by existing mTLS transport, not a dedicated scoped maintenance role; all-manager identity trust, CP fencing, reconfiguration race, operation drain and real Swarm integration remain release blockers. NEVER equate stored ACK count alone with safe-to-close.

## 2026-10-16 durable active admission fence (migration v9)
Each registered service/node mutation callback now inserts a durable `maintenance_active_admissions` row under the existing resource-lock MySQL session before invoking its callback, and deletes it only when the callback terminates. CLOSING admission checks the same cluster state, rejecting new callbacks. Crash/DB-error leftovers are conservatively retained and visible as `activeAdmissions` in scoped readiness. Such rows are not automatically expired or treated as completed: independent reconciliation is mandatory. Migration v9 adds a foreign-key-backed table without auto-opening any cluster. This is not sufficient to authorize CLOSED; all-manager ACK, unresolved operation and dispatch evidence, CP lease fencing, and direct Docker writer restriction remain necessary. CLOSED/RECONCILING/OPEN transitions are intentionally not exposed by this step.

## 2026-10-16 atomic CLOSED primitive (NOT publicly exposed)
The internal repository `commitClosed` takes the exact expected manager Agent ID set from an independently verified live all-manager barrier, locks the maintenance CLOSING state/generation in one InnoDB transaction, and refuses CLOSED if durable active admissions, nonterminal service/node operations, PREPARED/SENDING/UNCERTAIN dispatches, or mismatched/stale manager ACK records exist. The transition, generation increment and audit INSERT commit together; audit failure rolls the transaction back. A disposable real-MySQL test checks unresolved rejection, injected audit failure rollback, successful closure using **fixture-only synthetic ACKs**, and stale generation rejection. This is not production CLOSED authorization: no controller invokes it, an ACK table snapshot cannot independently prove changing Swarm manager membership, and CP ownership/fencing, administrator authorization, external Docker writer restrictions and real Swarm multi-manager acceptance remain unsatisfied. Never remove unresolved evidence automatically to force CLOSED; fixture cleanup is exclusively for the isolated MySQL PoC.

## 2026-10-16 scoped CLOSED confirmation (Draft only)
A scoped ADMIN POST `/v1/clusters/:clusterId/maintenance/confirm-closed` now requires both `DOCKLANE_MAINTENANCE_ENFORCE=1` and enforced fixed cluster registration, checks the current generation, blocks **each configured/live Swarm manager** through `MaintenanceManagerBarrier.blockAll`, and only then invokes an InnoDB CLOSED transaction that refuses nonterminal operations, active admissions and unresolved send evidence and verifies the exact manager ACK set. Missing manager, DB failure, stale state, audit failure and replay fail closed. Partial Agent blocks remain blocked and can be retried at the same generation after investigation. This endpoint remains unshipped while PR Draft: do not enable maintenance barrier in production until actual multi-manager Swarm acceptance, external Docker writer restrictions, CP lease/ownership fencing and recovery/reopen contract pass. A successful DB closure does not atomically fence external Docker CLI changes.
